# Technical Reference: SST Proxy Migration & Infrastructure Decision Log

## 1. System Architecture

This document outlines the technical configuration of the stateless Server-Side Tagging (SST) proxy deployed through Google Cloud App Engine, decoupled from a dedicated BigQuery warehouse project for enterprise-grade separation of concerns.

This repository contains two connected but distinct paths:

1. A live first-party SST infrastructure path.
2. A historical/demo reconciliation path using public GA4 sample data and synthetic Shopify data.

The demonstration reconciliation results must not be interpreted as measurements from live client traffic.

**Core Objectives:**

- Reduce client-side tracking loss by routing collection through a first-party SST proxy.
- Separate stateless ingestion infrastructure from the analytics warehouse through independent GCP projects and IAM boundaries.
- Support GA4 streaming export validation through the dedicated BigQuery warehouse.
- Apply mass-balance reconciliation and FMEA classification to representative ecommerce data.

## 2. Infrastructure Decision Log — Diagnosed During Build

Applying process-engineering discipline means treating every infrastructure deviation as a documented failure, tracing it to a root cause, and recording the corrective action.

The following infrastructure issues were diagnosed and corrected during deployment. They use the `INFRA-*` namespace so they remain distinct from the core data-pipeline FMEA register in `docs/fmea.md`.

| ID | Infrastructure Issue | Root Cause | Remediation | Status |
|---|---|---|---|---|
| **INFRA-01** | Proxy bootstrap failure | A billing block on the original GCP project caused App Engine initialization to fail; project checks returned no usable application. | Provisioned the dedicated `sst-portfolio-aniji` project and completed the required billing and App Engine setup. | Resolved |
| **INFRA-02** | False-negative health check | The health endpoint was tested against the wrong regional URL suffix, returning a false `404` and suggesting that the server was unavailable. | Corrected the regional suffix to `nn` for the Montreal deployment. | Resolved |
| **INFRA-03** | Attribution client misconfiguration | During a GTM container version update, the custom first-party GA4 client using server-managed FPID was mistakenly removed instead of the default GA4 client. | Rolled back the affected GTM version and republished the configuration with the intended client retained. | Resolved |

This log demonstrates the same discipline used in industrial process audits: each infrastructure deviation is separated from the downstream data failure modes and traced to a documented corrective action.

## 4. Mass Balance Validation

The reconciliation engine uses the verified SQL pipeline at `sql/ga4_shopify_mass_balance.sql`.

The demonstration path compares public GA4 sample purchase data against a synthetic Shopify setpoint using a BigQuery `FULL OUTER JOIN`. The synthetic setpoint includes controlled failure-mode injection for reconciliation testing.

Using this representative dataset, the engine isolated a **4.95% over-attribution error rate** and demonstrated how an estimated **$80,000 in phantom revenue** could be prevented from polluting media optimization models.

These are demonstration results derived from public GA4 sample data and synthetic Shopify data. They are not measurements from live client traffic.

The core data-pipeline failure modes are documented separately in `docs/fmea.md`, including:

- `FM-01`: Client-Side Tracker Suppression.
- `FM-03`: Phantom Purchase.

Continuous post-remediation drift monitoring, including a second measurement cycle showing the change in leak percentage after SST cutover, has not yet been completed. That follow-up measurement remains an open validation item.
